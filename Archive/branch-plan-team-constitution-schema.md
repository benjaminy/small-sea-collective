# Team Constitution Schema Plan

**Branch:** `team-constitution-schema`
**Archived:** Merged into `main` (fast-forward `a95fb22..b3bc317`) alongside `codex/permission-vocab`, which it was branched from. This branch's wrap-up (`design-record`) was written retroactively at archive time — see `Archive/design-record-team-constitution-schema.md`, which also folds in this branch's `NOTES.md` grounding survey.

## Goal

Turn the signed-append-only-teammate-history requirements already committed to in `architecture.md`
and `.IN_PROGRESS/codex-permission-vocab/FOLLOW-UP.md` into a concrete, field-level schema — precise
enough that the dependent implementation epics (mode-aware replication / #162, prepared recovery,
retention horizons, staleness observations) can be scoped and built against a single shared data model
instead of each inventing incompatible fragments of it.

This branch adopts the **Team Constitution** name (agreed in conversation) for the signed, append-only
governance lineage carried inside a team's Core berth, deliberately distinguished from **Core**, which
remains the berth/database that carries it.

This is a design/documentation branch. It does not change runtime code or the live `USER_SCHEMA_VERSION`.
It produces the schema that a later implementation branch builds against.

## Working assumption (stated up front, not settled by fiat)

Keep per-record-type SQL tables, matching the codebase's existing style (`key_certificate`,
`teammate_berth_storage_announcement`, `admission_proposal`), rather than one generic
type-tagged-JSON-blob table. The alternative (single generic table) would be more uniform but would
lose FK/uniqueness constraints the existing tables already rely on, and would abandon a style the
codebase already commits to. What *is* new: every record type shares one canonical envelope
(signing/anchor/versioning columns), generated by one shared helper, instead of each type
reimplementing `json.dumps(..., sort_keys=True)` independently as it does today.

If this tradeoff looks wrong once the concrete schema is in front of you, it's cheap to flip — no code
depends on it yet.

## Survey

See `Archive/design-record-team-constitution-schema.md` for the full grounding survey (moved there from this branch's `NOTES.md` at archive time). Summary: the canonical-signing idiom already exists,
duplicated three times with no shared helper; the anchor mechanism already exists in miniature,
scoped only to `admission_proposal`; `key_certificate` and `teammate_berth_storage_announcement` are
existing signed record families to reuse rather than replace; there is no migration system, so new
tables are just new `CREATE TABLE IF NOT EXISTS` statements when this becomes code.

## Implementation (of the design doc, not of runtime code)

1. Define one shared canonical envelope (fields, canonical-byte encoding, signature scheme, versioning)
   that every Constitution record type shares, generalizing the duplicated idiom found in the survey.
2. Generalize the existing `(anchor_commit, governance_digest)` pair from `admission_proposal` into a
   `constitution_anchor` referenced by every governance-bearing record type, backed by a full
   replayable-projection digest rather than an admission-specific admins/teammates/devices snapshot.
3. Define a generic `endorsement` / `finalization` pair usable by any proposal-shaped record (mode
   changes, exclusions, recovery — not only admission), fixing the current device-level dedupe gap by
   specifying teammate-level dedupe explicitly in the new type.
4. Enumerate every record type FOLLOW-UP.md commits to, classify each as reuse-existing,
   generalize-existing, or new, and give each a field-level shape.
5. Give the PII-bearing record types (display-name claim, teammate-unification claim, exclusion/reason)
   an explicit commitment+payload slot without picking the commitment scheme itself — that scheme is
   tracked separately in `Documentation/open-architecture-questions.md` and needs its own cryptographic
   analysis pass.
6. Sketch the replay/projection contract (what it means for `teammate`, `berth_role`, `invitation`,
   `team_device` to become rebuildable projections) at the level of an interface, not an implementation.
7. Write the result as `Documentation/team-constitution.md`, with `architecture.md` and the Manager spec
   pointing to it the way they already point to `linked-teams.md`.

## Validation

- Every record type in FOLLOW-UP.md's list is accounted for (reused, generalized, or newly defined) —
  no silent drops.
- Every field-level claim about existing code (table names, columns, function names) is checked against
  the actual source, not the spec prose, since the survey found the spec prose for B5 admission is
  already stale relative to the implemented SQL.
- The document does not pick the PII commitment scheme, the recovery anti-replay mechanism, or the
  staleness-to-checkpoint rule — those stay explicitly open, cross-referenced to where they're tracked,
  so this doc doesn't quietly foreclose decisions that were deliberately left open elsewhere.
- A reader can answer, for any two record types needing to interoperate (e.g. an exclusion record and
  an endorsement of it), exactly which fields they exchange and how a verifier checks the pair.
- `git diff --check` passes; no runtime file changes.

## Non-goals

- No new SQL tables land in `small-sea-manager` in this branch.
- No `USER_SCHEMA_VERSION` bump.
- No decision on the PII commitment scheme, recovery-ceremony anti-replay mechanics, or the
  staleness/checkpoint rule — placeholders only, explicitly marked as such.
- No mechanical rename of `berth_role`'s stored `read-write`/`read-only` values (unchanged, per the
  permission-vocab branch's own non-goals; this schema's new tables use the new `automatic` /
  `proposal-only` vocabulary directly since they are new tables with nothing to stay compatible with).
